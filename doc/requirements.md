# 产品需求

`opensource-release-watcher` 面向团队内部的开源组件治理场景，提供组件版本发布、已知漏洞风险和通知状态的持续跟踪能力。

## 1. 使用对象

| 角色 | 关注点 | 主要操作 |
| --- | --- | --- |
| 管理员 | 维护组件清单、检查策略和订阅关系 | 新增组件、编辑当前版本、配置订阅人、手动检查、查看记录 |
| 订阅人 | 关注组件更新和安全风险 | 接收邮件、查看通知记录 |

## 2. 核心场景

### 2.1 组件版本跟踪

系统维护团队正在使用的开源组件版本，并定期检查上游 GitHub Release / Tag。

关键结果：

- 当前内部使用版本。
- 上游最新版本。
- 是否存在版本更新。
- 最近检查时间和检查状态。
- Release Note 摘要和上游链接。

### 2.2 漏洞风险跟踪

系统基于当前内部使用版本解析 Git commit，并通过 OSV 查询公开已知漏洞。

关键结果：

- 当前版本是否命中 OSV 漏洞。
- 漏洞编号、摘要、严重性和证据链接。
- 可解析时给出建议升级版本。
- 组件只保留当前版本最近一次漏洞明细。

### 2.3 聚合通知

系统在一次组件检查完成后，将版本更新和漏洞风险合并成一封邮件。

通知需要包含：

- 组件名称和仓库地址。
- 当前使用版本。
- 版本检查结果。
- 漏洞检查结果。
- 漏洞明细和 OSV 链接。
- Release Note 摘要。
- 建议动作。

通知去重按 `组件 + 收件人 + 通知类型 + 检查结果指纹` 判断。

### 2.4 订阅管理

订阅人可以订阅全部组件，也可以只订阅指定组件。

系统按订阅人维护通知进度：

- 新版本通知基于订阅人自己的 `last_notified_version`。
- 新订阅人不会继承其他收件人的通知记录。
- 删除订阅人时清理对应邮箱的通知记录和订阅进度。

## 3. 功能范围

### 3.1 组件管理

- 新增、编辑、删除组件。
- GitHub 仓库地址创建后固定。
- 当前版本只允许向前升级，并且需要能在 GitHub Release / Tag 中解析。
- 支持启用或禁用检查。
- 支持手动检查单个组件。

### 3.2 检查记录

- 保存每次版本检查结果。
- 保存单个组件一次完整检查运行状态。
- 记录版本检查、漏洞检查和通知结果之间的关联。
- 检查记录保留最近记录，并保护仍被通知记录引用的记录。

### 3.3 漏洞检查

- 使用 OSV commit 查询能力。
- 当前版本无法解析到 commit 时显示“未识别”。
- OSV 查询失败时显示“检查失败”。
- 命中漏洞时显示“有漏洞”。
- 展示漏洞编号、摘要、严重性、建议升级版本和证据链接。

### 3.4 通知记录

- 保存每次邮件发送结果。
- 支持查看邮件正文快照。
- 支持按组件、收件人、状态、检查运行筛选。
- 支持测试邮件发送配置。

### 3.5 仪表盘

- 展示组件总数、更新数、漏洞数、检查异常和通知异常。
- 展示代理和 GitHub Token 的后台检测状态。
- 展示最近版本动态和通知状态。

运行状态检测由后端定时刷新缓存，页面刷新只读取缓存。

## 4. 非功能要求

| 分类 | 要求 |
| --- | --- |
| 可靠性 | 单个组件检查失败不影响其他组件 |
| 幂等性 | 相同检查结果不会重复通知同一收件人 |
| 可追溯性 | 检查记录、漏洞记录和通知记录可关联 |
| 部署方式 | 单机部署优先，SQLite 存储 |
| 配置方式 | 服务配置走 `.env`，组件和订阅数据走数据库 |
| 网络适配 | 支持 GitHub Token 和 HTTP/HTTPS 代理 |

## 5. 后续方向

- 更多漏洞来源，例如 GitHub Security Advisory。
- Release Note 关键字辅助分析。
- 通知优先级和分级策略。
- 周期性组件治理报告。
