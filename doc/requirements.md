# 开源组件版本监控系统需求文档

## 1. 项目概述

`opensource-release-watcher` 是一个用于持续监控开源组件版本和已知漏洞风险的 Web 服务。系统维护团队内部使用的开源组件清单，定期检查 GitHub Release / Tag 和 OSV 漏洞数据，当发现新版本或当前版本存在已知漏洞时通过邮件通知订阅人。

系统定位不是包管理器，也不是自动升级工具，而是开源组件版本变化感知服务。

## 2. 业务背景

团队项目通常依赖 protobuf、OpenCV、libevent、Eigen、zlib、OpenSSL 等开源组件。这些组件会不定期发布新版本，用于修复 Bug、修复安全漏洞、增加功能或调整接口行为。

如果完全依赖人工关注，容易出现以下问题：

- 新版本发布后无人感知。
- 安全修复没有及时同步。
- 多个项目使用不同版本，缺少统一管理。
- 组件订阅关系不明确。
- Release Note 无人跟踪。
- 升级评估和通知记录缺少留痕。

## 3. 用户角色

| 角色 | 说明 | 主要操作 |
| --- | --- | --- |
| 管理员 | 维护系统基础数据和组件清单 | 新增组件、编辑组件、配置订阅人、手动触发检查 |
| 普通订阅人 | 关注某些组件版本变化和安全风险 | 接收邮件通知、查看通知记录 |

## 4. 功能范围

### 4.1 组件清单管理

系统需要支持维护开源组件基础信息：

- 组件名称。
- GitHub 仓库地址，创建后不可修改。
- 当前内部使用版本，且只允许向前升级，不允许回退，并且必须能在 GitHub Release 或 Tag 历史中找到。
- 邮件订阅人。
- 检查策略。
- 是否启用检查。
- 备注信息。

### 4.2 版本检查

系统通过定时任务或手动触发执行版本检查：

- 优先查询 GitHub Release。
- 如果仓库没有 Release，则回退查询 Tag。
- 获取最新版本号、发布时间、Release Note、HTML 链接。
- 与本地记录的最近检查版本进行比较。
- 每次组件检查会创建一条检查运行记录，并保存版本检查结果。
- 版本检查完成后会触发当前版本的漏洞检查。
- 发现新版本时会进入本轮聚合通知判断。
- 未发现新版本时更新最近检查时间。

### 4.3 漏洞检查

系统通过 OSV 查询当前内部使用版本对应 commit 的公开漏洞：

- 将组件当前版本解析为 GitHub tag 或 commit。
- 使用 commit 查询 OSV 漏洞数据。
- 保存当前组件最新一次漏洞检查摘要和明细。
- 对同一个组件只保留当前版本最新一次漏洞明细，避免历史数据无限堆积。
- 当漏洞存在修复版本时，尝试转换为建议升级版本用于展示和通知。

### 4.4 通知管理

当前阶段只支持邮件通知：

- 对不同组件配置不同订阅人。
- 每轮组件检查完成后，将版本检查和漏洞检查聚合为一封邮件。
- 相同组件、收件人、通知类型和检查结果指纹只通知一次，避免重复发送。
- 每个订阅人与组件维护独立的已通知版本基线，新订阅人只接收其基线之后的新版本通知。
- 漏洞风险按通知指纹去重，新订阅人如果尚未接收过当前风险状态，在下一次检查后会收到一次通知。
- 邮件标题包含组件名称、版本变化和安全风险类型。
- 邮件正文包含当前使用版本、版本检查结果、漏洞检查结果、Release Note 摘要、发布时间和建议动作。
- 通知发送结果需要持久化。
- 删除全局订阅人时，需要同步清理该邮箱的历史通知记录和订阅进度记录。

### 4.5 检查结果展示

后台管理界面需要展示：

- 组件当前使用版本。
- 上游最新版本。
- 最近一次检查时间。
- 最近一次检查状态。
- 是否存在新版本。
- 是否已通知。
- Release Note 摘要。
- 最近一次漏洞状态。
- 漏洞明细和建议升级版本。

### 4.6 通知记录查看

系统需要支持查看历史通知记录：

- 通知组件。
- 通知版本。
- 通知类型。
- 收件人。
- 通知状态。
- 失败原因。
- 发送时间。

## 5. 核心流程

```text
定时调度触发检查任务
      ↓
读取启用状态的组件清单
      ↓
查询 GitHub Release
      ↓
无 Release 时查询 Tag
      ↓
解析最新版本和 Release Note
      ↓
与本地记录版本比较
      ↓
查询当前版本 OSV 漏洞风险
      ↓
汇总版本检查和漏洞检查结果
      ↓
生成检查记录、漏洞记录和邮件内容
      ↓
当版本或漏洞风险需要通知时发送邮件给订阅人
      ↓
保存通知记录
      ↓
更新组件最近检查状态
```

## 6. 非功能需求

| 分类 | 要求 |
| --- | --- |
| 可维护性 | 前后端分离，后端按 API、service、checker、storage、notifier 分层 |
| 可靠性 | 检查失败不影响其他组件，失败原因需要记录 |
| 幂等性 | 同一组件同一收件人对相同检查结果指纹不重复通知 |
| 可扩展性 | 后续可接入通知优先级和月度报告 |
| 部署复杂度 | 单机部署优先，SQLite 存储，减少外部依赖 |
| 配置方式 | Microsoft Graph 发信参数、监听端口、GitHub Token 等走服务端配置；组件数据走数据库维护 |

## 7. 版本一期边界

一期只实现以下能力：

- React + TypeScript + Vite + Ant Design 管理前端。
- Go HTTP API Server。
- SQLite 持久化。
- GitHub Release / Tag 查询。
- 定时检查和手动检查。
- OSV 漏洞检查。
- 邮件通知。
- 组件、订阅人、检查记录、通知记录管理。

一期不实现以下能力：

- 自动升级依赖。
- 多租户权限系统。
- Webhook 触发。
- 非 GitHub 代码托管平台。
- 钉钉、飞书、Slack 等非邮件通知。
